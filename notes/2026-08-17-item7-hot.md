## 2. The Problem HOT Solves

In Item 6, we saw that **every update** created a brand-new tuple at a new CTID, forcing every secondary index on the table to insert a new pointer:

```text
WITHOUT HOT (Standard Non-In-Place Update):
  UPDATE items SET price = 20 WHERE item_id = 100;
  -> New tuple at CTID (0, 2)
  -> idx_item_id:     INSERT (100 -> (0, 2))    <-- Index write!
  -> idx_created_at:  INSERT (ts -> (0, 2))      <-- Index write!
  -> idx_category:    INSERT (cat -> (0, 2))     <-- Index write!
  
  Total index writes: 3 (one per index), even though only "price" changed!
```

### HOT Prerequisites:
A **Heap-Only Tuple** update is eligible if and only if:
1. **No indexed column changed** (only non-indexed columns like `price` were modified).
2. **The new tuple fits on the same 8KB page** as the old tuple.

When both conditions hold, PostgreSQL avoids touching any index at all.

## 3. The HOT Update Mechanism

```text
WITH HOT:
  UPDATE items SET price = 20 WHERE item_id = 100;
  -> New tuple at CTID (0, 2) ON SAME PAGE
  -> Index entries: UNCHANGED (still only 1 entry: 100 -> (0, 1))!
  
  Page 0 Physical Layout:
  +-------------------------------------------------------------------------+
  | Slot 1: [xmin=1, xmax=3, HEAP_HOT_UPDATED] price=$10  t_ctid=(0,2)     |
  |     |                                                                   |
  |     +---------> HOT CHAIN --------->                                    |
  |                                                                         |
  | Slot 2: [xmin=3, xmax=0, HEAP_ONLY_TUPLE] price=$20  t_ctid=(0,2)      |
  +-------------------------------------------------------------------------+
```

### Step-by-Step:
1. Old tuple at Slot 1 gets: `xmax = tx_id`, `t_ctid = (0, 2)`, `infomask |= HEAP_HOT_UPDATED`.
2. New tuple at Slot 2 gets: `xmin = tx_id`, `infomask = HEAP_ONLY_TUPLE`.
3. **Zero index writes!** All secondary indexes still point to `(0, 1)`.
4. On subsequent lookups, `index_lookup()` follows the on-page HOT chain from `(0, 1)` $\rightarrow$ `(0, 2)`.

## 4. HOT-Chain-Following Index Lookups

```text
  Index entry: [Key 100 -> CTID (0, 1)]
                                |
                                v
  Heap Page 0, Slot 1:  is_tuple_visible() -> NOT visible (xmax = 3, committed)
                         infomask & HEAP_HOT_UPDATED? -> YES!
                         Follow t_ctid -> (0, 2)
                                |
                                v
  Heap Page 0, Slot 2:  is_tuple_visible() -> VISIBLE! Return price = $20
```

### Multi-Hop Chains:
HOT chains can be more than one hop. After multiple updates:
$$\text{Slot 1} \xrightarrow{t\_ctid} \text{Slot 2} \xrightarrow{t\_ctid} \text{Slot 3}$$

The index still has **exactly 1 entry** pointing to Slot 1. The chain traversal finds the latest visible version.

## 7. Quiz Diagnostics & Graded Mechanics

### Q1 · HOT Update Eligibility (`HOT-ELIGIBILITY`)
- **Question**: Under what two conditions is an update eligible for HOT?
- **Answered**: Option 2 (No indexed columns modified AND new tuple version fits on the same 8KB page) ✅
- **Mechanism**:
  If an indexed column is modified, the index key itself changes, requiring a new index entry. If the new version does not fit on the same page, external indexes would need a new `page_id` pointer. When both conditions hold, the new version is placed on the same page and chained via `t_ctid` with **zero secondary index writes**.

---

### Q2 · On-Page HOT Chain Traversal (`HOT-CHAIN-TRAVERSAL`)
- **Question**: How does `index_lookup` retrieve the correct visible version when landing on a `HEAP_HOT_UPDATED` tuple?
- **Answered**: Option 2 (Evaluates `is_tuple_visible()` on `(0, 1)`, sees it is not visible, checks `HEAP_HOT_UPDATED` flag, and follows `t_ctid` on Page 0 to inspect `(0, 2)`) ✅
- **Mechanism**:
  Secondary indexes continue pointing exclusively to the root line pointer (`(0, 1)`). The query engine dereferences to the root tuple and traverses the in-page version chain, avoiding any need to touch or dirty secondary index pages.

---

### Q3 · Long HOT Chains and Page Pruning (`HOT-CHAIN-BLOAT`)
- **Question**: What is the performance impact of 200 consecutive HOT updates on the same page, and how is it resolved?
- **Answered**: Option 1 (Index lookups must traverse the 200-hop chain; PostgreSQL resolves this during page pruning by converting the root line pointer to a direct `REDIRECT` line pointer pointing straight to the newest tuple, collapsing the chain) ✅
- **Mechanism**:
  During HOT pruning (which happens during normal queries or vacuum), PostgreSQL detects intermediate dead tuples in the chain, frees their tuple bytes, and marks the root line pointer with `ItemFlags::REDIRECT` pointing directly to the live successor. This collapses the multi-hop chain into a direct single-hop jump.
