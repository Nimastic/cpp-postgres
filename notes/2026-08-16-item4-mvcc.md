## 2. The Core Philosophy of PostgreSQL MVCC

In relational databases, concurrency without blocking is achieved through **Multi-Version Concurrency Control (MVCC)**:
> **"Readers never block Writers, and Writers never block Readers."**

### Why PostgreSQL Never Updates In-Place:
When an item's price is updated from $\$10$ to $\$20$:
1. The physical row at Slot 1 is **NOT overwritten**.
2. Instead, the database leaves the $\$10$ tuple intact, stamps its `xmax = tx_id` (marking the end of its life for future transactions), and appends a **brand new tuple version** at Slot 2 with `price = $20` and `xmin = tx_id`.
3. Both versions exist simultaneously on the exact same 8KB page.
4. Active transactions use their **Snapshot** to look back in time and select the exact row version valid during their point in time.

```text
                                  Page 0
+-------------------------------------------------------------------------+
| Line Pointers:                                                          |
|   Slot 1: offset=8168 | Slot 2: offset=8144                             |
+-------------------------------------------------------------------------+
|                                                                         |
| Tuple Slot 2 (New Version):                                             |
|   [ xmin = 3 | xmax = 0 | t_ctid = (0,2) ] -> data: (100, $20)          |
|                                                                         |
| Tuple Slot 1 (Old Version):                                             |
|   [ xmin = 1 | xmax = 3 | t_ctid = (0,2) ] -> data: (100, $10)          |
+-------------------------------------------------------------------------+
```

## 2. The Snapshot Data Structure

In PostgreSQL, a `Snapshot` defines an observer's **visibility horizon**:

```cpp
struct Snapshot {
    tx_id_t current_tx_id{0};                 // My own transaction ID
    tx_id_t xmin{0};                          // All tx < xmin are committed and visible
    tx_id_t xmax{0};                          // All tx >= xmax are in the future (invisible)
    std::unordered_set<tx_id_t> active_txs{}; // Transactions in-progress at snapshot time
};
```

### The Visibility Horizon:
```text
  Transactions < xmin       xmin <= Active < xmax       Transactions >= xmax
+-----------------------+---------------------------+---------------------------+
|    ALL COMMITTED      |    IN-PROGRESS AT START   |       IN THE FUTURE       |
|    ALWAYS VISIBLE     |         INVISIBLE         |         INVISIBLE         |
+-----------------------+---------------------------+---------------------------+
```

## 3. The Two-Phase Visibility Algorithm (`is_tuple_visible`)

To determine if a tuple version is visible to a transaction snapshot:

```text
                          [ TupleHeader: xmin, xmax ]
                                       |
                                       v
                    +-------------------------------------+
                    | Phase 1: Did creator (xmin) commit  |
                    |       before our snapshot?          |
                    +-------------------------------------+
                                  /         \
                             NO  /           \  YES
                                v             v
                         [ INVISIBLE ]   +-------------------------------------+
                                         | Phase 2: Was tuple deleted (xmax)   |
                                         |       before our snapshot?          |
                                         +-------------------------------------+
                                                       /         \
                                                  YES /           \  NO
                                                     v             v
                                              [ INVISIBLE ]   [ VISIBLE ]
```

### Phase 1: Creator (`xmin`) Evaluation
1. **Self-created:** If `xmin == current_tx_id` $\rightarrow$ **xmin holds**.
2. **Aborted / In-Progress:** If `xmin` status is `ABORTED` or `IN_PROGRESS` $\rightarrow$ **INVISIBLE** (uncommitted write).
3. **Committed:**
   - If `xmin >= snapshot.xmax` $\rightarrow$ **INVISIBLE** (created in the future).
   - If `snapshot.active_txs.contains(xmin)` $\rightarrow$ **INVISIBLE** (creator was uncommitted when snapshot froze).
   - Otherwise $\rightarrow$ **xmin holds**.

### Phase 2: Deleter (`xmax`) Evaluation
1. **Not Deleted:** If `xmax == 0` $\rightarrow$ **VISIBLE**.
2. **Self-deleted:** If `xmax == current_tx_id` $\rightarrow$ **INVISIBLE**.
3. **Aborted / In-Progress:** If `xmax` is `ABORTED` or `IN_PROGRESS` $\rightarrow$ Deletion did not take effect $\rightarrow$ **VISIBLE**.
4. **Committed:**
   - If `xmax >= snapshot.xmax` $\rightarrow$ Deleted in our future $\rightarrow$ **VISIBLE** in this snapshot.
   - If `snapshot.active_txs.contains(xmax)` $\rightarrow$ Deleter was still running when snapshot froze $\rightarrow$ **VISIBLE**.
   - If `xmax < snapshot.xmin` $\rightarrow$ Deleted before our snapshot $\rightarrow$ **INVISIBLE**.

## 4. Tracing the Video Proof Scenario

```text
Timeline:
t1: Tx 1 (xmin=1) INSERT (100, $10) -> COMMITTED
t2: Tx 2 (xmin=2) BEGIN SNAPSHOT     -> snap2 = {xmin=3, xmax=3}
t3: Tx 3 (xmin=3) UPDATE (100, $20) -> stamps Slot 1 xmax=3, inserts Slot 2 xmin=3 -> COMMITTED
t4: Tx 4 (xmin=4) BEGIN SNAPSHOT     -> snap4 = {xmin=2, xmax=5}
```

### Evaluating Tx 2 Query:
- **Slot 1 (`xmin=1, xmax=3, $10`)**:
  - `xmin = 1 < snap2.xmin (3)` $\rightarrow$ Created before snapshot $\rightarrow$ **Valid**.
  - `xmax = 3 >= snap2.xmax (3)` $\rightarrow$ Deleted in the future $\rightarrow$ **Visible**.
  - **Result: Tx 2 returns `$10`**!
- **Slot 2 (`xmin=3, xmax=0, $20`)**:
  - `xmin = 3 >= snap2.xmax (3)` $\rightarrow$ Created in the future $\rightarrow$ **Invisible**.

### Evaluating Tx 4 Query:
- **Slot 1 (`xmin=1, xmax=3, $10`)**:
  - `xmin = 1 < snap4.xmin (2)` $\rightarrow$ Created before snapshot $\rightarrow$ **Valid**.
  - `xmax = 3 < snap4.xmax (5)` and committed $\rightarrow$ Deleted before snapshot $\rightarrow$ **Invisible**.
- **Slot 2 (`xmin=3, xmax=0, $20`)**:
  - `xmin = 3 < snap4.xmax (5)` and committed $\rightarrow$ Created before snapshot $\rightarrow$ **Valid**.
  - `xmax = 0` $\rightarrow$ Alive $\rightarrow$ **Visible**.
  - **Result: Tx 4 returns `$20`**!

## 7. Quiz Diagnostics & Graded Mechanics

### Q1 · Snapshot Horizon Visibility (`MVCC-SNAPSHOT`)
- **Question**: Is a tuple with `xmin = 30` visible to a snapshot with `xmin = 10, xmax = 25`?
- **Answered**: Option 2 (No, $\text{xmin} = 30 \ge \text{snapshot.xmax} (25)$) ✅
- **Mechanism**:
  Any transaction with $\text{tx\_id} \ge \text{snapshot.xmax}$ was assigned after the snapshot was frozen in time. Tuples created by future transactions are completely invisible to earlier snapshots.

---

### Q2 · Aborted Transaction XMAX Rollback (`XMAX-ROLLBACK`)
- **Question**: Why is a tuple whose `xmax = 7` still visible after Transaction 7 aborts?
- **Answered**: Option 2 (`is_tuple_visible` checks status in `TransactionManager`; `ABORTED` status ignores the deletion) ✅
- **Mechanism**:
  PostgreSQL avoids writing to disk during an `ABORT` (which would cause massive random I/O during rollbacks). Instead, it leaves `xmax = 7` stamped on the page and simply records `status = ABORTED` in the transaction status log. When readers evaluate `xmax`, they see it aborted and treat the row as still alive.

---

### Q3 · Snapshot Pinning & Table Bloat (`SNAPSHOT-PINNING`)
- **Question**: Why does an 8:00 AM transaction prevent `VACUUM` from cleaning up dead tuples modified at 11:00 AM?
- **Answered**: Option 2 (The 8:00 AM transaction's snapshot still requires seeing the old version; removing it causes snapshot corruption) ✅
- **Mechanism**:
  A tuple is only **truly dead** when its `xmax` is older than the oldest active transaction snapshot in the entire database:
  $$\text{xmax} < \min(\text{active\_snapshots.xmin})$$
  As long as that 8:00 AM transaction is open, it "pins" the visibility horizon back at 8:00 AM, forcing PostgreSQL to retain all intervening dead tuples $\rightarrow$ leading to table bloat.
