## 2. The Problem TOAST Solves

In PostgreSQL:
1. Disk pages are fixed at **8KB** (`PAGE_SIZE = 8192`), and rows **cannot span across physical page boundaries**.
2. If a user inserts a **20KB text document**, a **100KB JSON payload**, or a **5MB image**, it physically cannot fit on a single 8KB slotted page.
3. Even if a 4KB row *could* fit, putting large attributes inline on the main heap table would cause catastrophic **table bloat**, drastically reducing the number of rows per page and crippling sequential scan performance.

**TOAST (The Oversized-Attribute Storage Technique)** solves this by storing large variable-length attributes in an auxiliary side table and keeping only an 18-byte pointer in the main tuple:

```text
       MAIN HEAP TABLE (Page 0)                 AUXILIARY TOAST TABLE (Side File)
 +----------------------------------+          +----------------------------------+
 | Slot 1: item_id=1, price=$100    |          | Chunk (id=1, seq=0) [2048 bytes] |
 |   ToastPointer (18 Bytes):       |          | Chunk (id=1, seq=1) [2048 bytes] |
 |   [id=1, raw_size=20481, chunks=11]───►     | Chunk (id=1, seq=2) [2048 bytes] |
 |                                  |          | ...                              |
 | Slot 2: item_id=2, price=$200    |          | Chunk (id=1, seq=10)[  81 bytes] |
 |   ToastPointer (18 Bytes):       |          +----------------------------------+
 |   [id=2, raw_size=20481, chunks=11]───►     | Chunk (id=2, seq=0) [2048 bytes] |
 +----------------------------------+          +----------------------------------+
```

---

## 3. Thresholding & Slicing Strategy

PostgreSQL applies a **$\frac{1}{4}$ Page Size Rule**:
- **Inline Payload ($\le 2048$ Bytes)**: Stored directly inline in the tuple payload (`ToastStorageType::INLINE`). Zero auxiliary table overhead.
- **Out-of-Line Payload ($> 2048$ Bytes)**: Sliced into individual **2KB chunks** (`TOAST_CHUNK_SIZE = 2048`) and written to the dedicated TOAST relation (`ToastStorageType::OUT_OF_LINE`).

---

## 4. The 18-Byte `ToastPointer`

When an attribute is TOASTed, the main table replaces the multi-kilobyte data with a packed 18-byte pointer:

```cpp
#pragma pack(push, 1)
struct ToastPointer {
    uint64_t toast_id{0};       // Unique 64-bit ID identifying this toasted value (8B)
    uint32_t raw_size{0};       // Full uncompressed byte size (4B)
    uint32_t chunk_count{0};    // Number of 2KB chunks stored in TOAST table (4B)
    uint16_t flags{0};          // Storage & compression status flags (2B)
};
#pragma pack(pop)
```

---

## 5. Multi-Page Reassembly

Upon executing a query that reads a TOASTed column:
1. The engine inspects `ToastPointer`.
2. Fetches all $N$ chunks $0, 1, \dots, \text{chunk\_count}-1$ from the auxiliary TOAST table in sequential order.
3. Glues the chunks back together in RAM into the original uncompressed string or binary payload.
