## 2. The Problem WAL Solves (Durability without Slow Random I/O)

In Item 8, we established that PostgreSQL modifies pages in RAM (`shared_buffers`) and delays writing dirty pages to disk to avoid thousands of slow random disk seeks.

However, if the operating system crashes or power fails while dirty pages are sitting in RAM:
- Data modified by committed transactions would be lost.
- Partial page writes could leave on-disk pages torn or corrupt.

**Write-Ahead Logging (WAL)** solves this by appending tiny sequential log records to an append-only file (`wal.log`):

```text
               TRANSACTION COMMIT
                       |
                       v
        +-------------------------------+
        | 1. Append WAL Record (RAM)    |
        +-------------------------------+
                       |
                       v
        +-------------------------------+
        | 2. Force Flush WAL to Disk    |  <-- Fast sequential append (fsync)
        +-------------------------------+
                       |
                       v
        [ TRANSACTION CONFIRMED COMMITTED TO CLIENT ]
                       :
                       v (Later, asynchronously)
        +-------------------------------+
        | 3. Dirty Pages Flushed to Disk|  <-- By Checkpoint or Eviction
        +-------------------------------+
```

---

## 3. The Write-Ahead Rule

> **"A dirty page frame in `shared_buffers` must NEVER be written to table files on disk until the WAL record describing that change has already been written and flushed to `wal.log` on disk!"**
> $$\text{page.header.pd\_lsn} \le \text{wal.flushed\_lsn}$$

If this invariant were violated, a crash after writing the table page but before writing the WAL would make uncommitted changes permanent with no log record to undo them!

---

## 4. Binary Log Record Layout

Each binary log entry in `wal.log` contains a fixed **35-byte packed header** followed by variable payload bytes:

```cpp
#pragma pack(push, 1)
struct WALRecordHeader {
    lsn_t         lsn{0};            // Byte offset of this record in WAL (8B)
    lsn_t         prev_lsn{0};       // Byte offset of previous record (8B)
    tx_id_t       tx_id{0};          // Transaction that produced this log (4B)
    WALRecordType type{0};           // INSERT, UPDATE, COMMIT, ABORT (1B)
    page_id_t     page_id{0};        // Affected heap page ID (4B)
    slot_id_t     slot_id{0};        // Affected slot ID (2B)
    uint32_t      payload_len{0};    // Byte length of payload (4B)
    uint32_t      crc{0};            // CRC32 checksum of header + payload (4B)
};
#pragma pack(pop)
```

## 5. Crash Recovery: The ARIES REDO Replay Engine

When PostgreSQL restarts after a crash:

```text
                     [ wal.log on Disk ]
                              |
                              v
             +----------------------------------+
             | PASS 1: SCAN & STATUS RECOVERY   |
             | - Validate CRC32 of each record  |
             | - Reconstruct status of all TXs: |
             |   COMMITTED vs ABORTED           |
             +----------------------------------+
                              |
                              v
             +----------------------------------+
             | PASS 2: REDO REPLAY              |
             | For each record in WAL:          |
             |   If page.pd_lsn <= rec.lsn:     |
             |     Replay change to page        |
             |     page.pd_lsn = record_end_lsn |
             +----------------------------------+
                              |
                              v
        [ Database Restored to Exact Pre-Crash State! ]
```

### LSN Idempotency:
Because some pages may have been flushed to disk before the crash while others were not, recovery checks:
$$\text{page.header.pd\_lsn} \le \text{rec.header.lsn}$$
If `page.header.pd_lsn > rec.header.lsn`, the page already contains this modification on disk, and the record is safely skipped.

## 8. Quiz Diagnostics & Graded Mechanics

### Q1 · Write-Ahead Rule Invariant (`WAL-WRITE-AHEAD-INVARIANT`)
- **Question**: What is the core Write-Ahead Logging invariant enforced before writing dirty pages to disk?
- **Answered**: Option 2 ($\text{page.header.pd\_lsn} \le \text{wal.flushed\_lsn}$: a dirty page frame in `shared_buffers` must never be written to table files on disk until the WAL record describing that change has already been written and flushed to `wal.log` on disk) ✅
- **Mechanism**:
  If a dirty page were flushed to disk before its WAL record, a sudden crash would leave uncommitted changes on disk with no log record to undo or replay, permanently corrupting database consistency.

---

### Q2 · REDO LSN Idempotency During Crash Recovery (`REDO-LSN-IDEMPOTENCY`)
- **Question**: How does the REDO engine handle a log record at `LSN = 200` when the disk page has `pd_lsn = 250`?
- **Answered**: Option 2 (Because $\text{page.pd\_lsn} > \text{rec.lsn}$ ($250 > 200$), the engine knows this page was already written to disk after this modification occurred; it safely skips re-inserting the tuple, preventing duplicate rows) ✅
- **Mechanism**:
  Crash recovery re-runs history. Because checkpointing or buffer eviction may have written some pages to disk prior to the crash while other pages were only in RAM, checking `page.pd_lsn <= rec.lsn` guarantees that every log record is applied **exactly once** (idempotency).

---

### Q3 · Sequential Log Append vs Random Page I/O (`FLUSH-ON-COMMIT-COST`)
- **Question**: Why is flushing a 35-byte `COMMIT` record to the WAL fast enough for every commit, while flushing dirty 8KB table pages would crush throughput?
- **Answered**: Option 1 (WAL writes are strictly **sequential appends** to the end of a single file minimizing disk arm movement, whereas table page writes require **random I/O seeks** across arbitrary 8KB page offsets across different table files) ✅
- **Mechanism**:
  Sequential disk writes approach raw hardware bandwidth (hundreds of MB/s or GB/s). Random disk writes require filesystem metadata lookups and physical head seeks/rotations, resulting in a $1000\times$ throughput penalty.
