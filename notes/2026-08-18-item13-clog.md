## 2. The Problem CLOG Solves

In Items 1–12:
- `TransactionManager` kept transaction commit/abort statuses in an in-memory `std::unordered_map<tx_id_t, TransactionStatus>`.
- Upon crash or engine restart, this map was lost and all transactions appeared `IN_PROGRESS`, requiring a slow, full WAL replay to discover which transactions committed.

**CLOG (`pg_xact/`)** provides a compact, persistent on-disk bitmap where each transaction status is encoded in exactly **2 bits**:

```text
               8KB CLOG PAGE (32,768 Transactions per Page)
 ┌──────────────────────────────────────────────────────────────────────────┐
 │ Byte 0: [ Tx 3 (2b) ][ Tx 2 (2b) ][ Tx 1 (2b) ][ Tx 0 (2b) ]             │
 │ Byte 1: [ Tx 7 (2b) ][ Tx 6 (2b) ][ Tx 5 (2b) ][ Tx 4 (2b) ]             │
 │ ...                                                                      │
 │ Byte 8191: [ Tx 32767 ][ Tx 32766 ][ Tx 32765 ][ Tx 32764 ]             │
 └──────────────────────────────────────────────────────────────────────────┘
```

### 2-Bit Status Encoding:
- `00` = `IN_PROGRESS`
- `01` = `COMMITTED`
- `10` = `ABORTED`
- `11` = `SUB_COMMITTED` (subtransactions)

## 3. Math & Page Indexing

For any arbitrary 64-bit transaction ID `tx_id`:
- **Page ID**: $\text{page\_id} = \lfloor \frac{\text{tx\_id}}{32768} \rfloor$
- **Byte Offset**: $\text{byte\_offset} = \lfloor \frac{\text{tx\_id} \pmod{32768}}{4} \rfloor$
- **Bit Shift**: $\text{bit\_shift} = (\text{tx\_id} \pmod 4) \times 2$

## 6. Quiz Diagnostics & Graded Mechanics

### Q1 · 2-Bit CLOG Density (`CLOG-2BIT-BITMAP`)
- **Question**: How many transaction statuses can be stored on a single 8KB CLOG page?
- **Answered**: Option 2 (**32,768 transactions** ($8,192 \text{ bytes} \times 4 \text{ transactions/byte}$)) ✅
- **Mechanism**:
  Because each transaction only requires 4 discrete states (`IN_PROGRESS = 00`, `COMMITTED = 01`, `ABORTED = 10`, `SUB_COMMITTED = 11`), 2 bits are sufficient. Packing 4 transactions per byte yields 32,768 transactions per 8KB page, meaning 1 million transactions take only ~30 pages (240 KB)!

---

### Q2 · Bitmap Offset and Shift Math (`CLOG-BIT-EXTRACTION-MATH`)
- **Question**: Compute the page, byte, and bit offset for `tx_id = 10`.
- **Answered**: Option 2 (`page_id = 0, byte_offset = 2, bit_shift = 4`) ✅
- **Mechanism**:
  - $\text{page\_id} = \lfloor 10 / 32768 \rfloor = 0$
  - $\text{byte\_offset} = \lfloor (10 \bmod 32768) / 4 \rfloor = \lfloor 10 / 4 \rfloor = 2$
  - $\text{bit\_shift} = (10 \bmod 4) \times 2 = 2 \times 2 = 4$
  - Accessing byte 2 and shifting right by 4 bits isolates bits `5..4`, giving the exact 2-bit status for transaction 10.

---

### Q3 · WAL vs CLOG Separation of Concerns (`CLOG-MVCC-INDEPENDENCE`)
- **Question**: Why does PostgreSQL maintain both a WAL and a persistent CLOG on disk?
- **Answered**: Option 1 (WAL logs are append-only time-series records that grow indefinitely and are archived/truncated, whereas CLOG provides an $O(1)$ random-access array on disk where the MVCC engine can check the commit status of any transaction ID in nanoseconds without scanning gigabytes of log history) ✅
- **Mechanism**:
  WAL provides sequential crash durability and undo/redo streams. CLOG provides persistent, indexed transaction metadata for MVCC visibility evaluations on running queries.
