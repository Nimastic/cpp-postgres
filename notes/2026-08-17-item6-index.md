## 2. The Core Philosophy of PostgreSQL Secondary Indexes

In PostgreSQL, secondary indexes are **pure key-to-CTID maps**:
1. Indexes do **NOT** store row data (e.g. `price`).
2. Indexes do **NOT** store MVCC transaction headers (`xmin`, `xmax`).
3. Indexes simply store:
   $$\text{Key} \longrightarrow \text{CTID}(page\_id, slot\_id)$$

```text
               B-Tree Index on "item_id"
               +-----------------------+
               | Key: item_id = 100    |
               | Values: (0,1), (0,2)  |
               +-----------+-----------+
                          / \
          CTID (0,1)     /   \     CTID (0,2)
                        v     v
   +-----------------------------------------------+
   | Slot 1: [xmin=1, xmax=3] -> price = $10       |  (Page 0 in HeapFile)
   | Slot 2: [xmin=3, xmax=0] -> price = $20       |
   +-----------------------------------------------+
```

## 3. The Index-Assisted Query Pipeline (`index_lookup`)

When executing `SELECT price FROM items WHERE item_id = 100`:

```text
  [ Query: item_id = 100 ]
             |
             v
  +----------------------+
  | Search B-Tree Index  | ----> Returns candidate CTIDs: [(0, 1), (0, 2)]
  +----------------------+
             |
             v
  +----------------------+
  | Dereference Heap     | ----> Fetches Slot 1 (xmin=1, xmax=3, $10)
  | at candidate CTIDs   | ----> Fetches Slot 2 (xmin=3, xmax=0, $20)
  +----------------------+
             |
             v
  +----------------------+
  | is_tuple_visible()   | ----> Evaluates against current Snapshot!
  +----------------------+
             |
             v
  [ Returns: $10 for Tx 2 Snapshot | $20 for Tx 4 Snapshot ]
```

## 4. The Write Amplification Problem (Why Updates are "Ugly")

In standard PostgreSQL without optimizations:
- When a row is updated from $\$10$ to $\$20$, the database creates a new tuple version at `CTID(0, 2)`.
- Because the new tuple lives at a **new CTID**, PostgreSQL is forced to insert a brand new entry into **every single index** on that table:
  - `idx_item_id`: adds `(100 -> (0, 2))`
  - `idx_created_at`: adds `(timestamp -> (0, 2))`
  - `idx_category`: adds `(category -> (0, 2))`
- Even if only `price` changed, all 3 indexes suffer write amplification and bloat!

This critical problem is the direct motivation for **HOT (Heap-Only Tuples)** in Item 7.

## 7. Quiz Diagnostics & Graded Mechanics

### Q1 · Index Payload Isolation (`INDEX-PAYLOAD-ISOLATION`)
- **Question**: Why doesn't a PostgreSQL secondary B-Tree index store `xmin` and `xmax` inside index leaf nodes?
- **Answered**: Option 1 (Indexes only map $\text{Key} \rightarrow \text{CTID}$; keeping MVCC headers strictly in the heap prevents index bloat and eliminates index writes during transaction status changes) ✅
- **Mechanism**:
  Decoupling indexes from transaction state means transactions committing or aborting only write to status logs without dirtying index pages. All visibility arbitration is deferred to the heap tuple header.

---

### Q2 · Multi-Version Index Dereferencing (`MULTI-VERSION-INDEX-DEREFERENCE`)
- **Question**: When an index lookup returns candidate CTIDs `(0, 1)` and `(0, 2)`, how is the correct version chosen?
- **Answered**: Option 2 (The engine dereferences both CTIDs into the heap, reads raw `TupleHeader` for each slot, runs `is_tuple_visible()` against the snapshot, and returns the single visible version) ✅
- **Mechanism**:
  The index serves as an access accelerator to narrow millions of rows down to $k$ physical candidate CTIDs. The heap provides ground truth for MVCC visibility.

---

### Q3 · Index Write Amplification Without HOT (`INDEX-WRITE-AMPLIFICATION`)
- **Question**: Why does updating an unindexed column cause write amplification across all 5 indexes?
- **Answered**: Option 1 (Non-in-place update places the new tuple at a new CTID `(0, 2)`, forcing every index on the table to add a new pointer to `(0, 2)` even if indexed column values didn't change) ✅
- **Mechanism**:
  Because secondary indexes store physical CTIDs, changing a tuple's physical address requires updating every index on the table. This is the exact bottleneck that **Heap-Only Tuples (HOT)** solves in Item 7.
